# Copy and i18n

Every user-facing string in this app goes through the catalogue in `services/i18n/locales/en.json`, and a lint rule
enforces it. This document says what that covers, what it deliberately does not, and how to
add copy without breaking the build.

## The problem this settles

The rule that no new hardcoded user-facing string should be added lived only in an untracked
agent-guidance file. There was no CONTRIBUTING, and the only mention in tracked docs
described a much narrower scope. The code disagreed with the rule, comprehensively:

- `services/i18n.ts` held **53 keys** across five namespaces.
- `app/`, `components/` and `view-models/` held roughly **260** hardcoded user-facing
  strings.
- Six of 23 screens used i18n at all. Seventeen were entirely hardcoded, including three of
  the four tabs.

Coverage was about 21%, so the rule was unenforceable in practice: following it inside a
screen where nothing else was translated produced a file with three keys and thirty
literals, which serves a translator worse than either consistent choice. The disagreement
got resolved ad hoc every time somebody wrote a line of copy.

The catalogue now holds **246 keys**, and the rule applies to every file that renders copy.

## What is enforced

`eslint.config.js` runs `i18next/no-literal-string` as an **error** over:

- `app/**/*.tsx`
- `components/**/*.tsx`
- `view-models/**/*.ts`
- `constants/**/*.ts`

Tests are excluded: they assert on copy, they are not copy.

### How the rule is tuned, and why

`mode: 'all'`. An earlier version used `jsx-only`, and the gap was not subtle: it inspects
JSX text and JSX attributes, so copy living in a data structure was never looked at. Whole
screens read as clean while most of their copy sat in a const above them --
`{ label: '4 Active' }`, the profile navigation, the error strings a view-model returns.

`all` means every literal, so the noise has to be filtered or the rule becomes unusable:

- `object-properties.include` names the copy-bearing property names.
- `callees.exclude` drops `console.*`, `require`, `Error`, and the `t` functions.
- `words.exclude` drops URLs, `sha256/` prefixes, strings with no letters, route paths,
  hex colours, and **any single lowercase token**. That last one carries most of the weight:
  in this codebase a lowercase identifier is a state enum (`idle`, `searching`), a
  capability (`power`), a theme value (`dark`), or a screen id, while copy starts with a
  capital or contains a space. It separates them without a wordlist that would need
  maintaining.

One trap if you edit those patterns: the plugin wraps each in `^…$` for a whole-string
match, so a leading `^` produces `^^…$` and silently matches nothing. The trailing `.*` is
load-bearing.

A second trap, and a worse one, because it hid a third of the copy while every check read green:
**the plugin skips every string inside a variable whose name is all capitals.** Its
`VariableDeclarator` handler treats `const A_B = ...` as a constant and exempts everything under
it, and this codebase keeps copy in exactly such constants -- `STEP_LABELS`, `SUGGESTED_PROMPTS`,
a privacy screen's paragraphs. `{ title: 'Data Collection' }` was flagged in `const sections` and
passed in `const SECTIONS`. The plugin has no option for it, so `eslint.config.js` wraps the rule
and drops that handler. `services/__tests__/i18n-rule.test.ts` runs the real ESLint command line
against an all-caps constant, so a plugin upgrade or a tidy-up that removes the wrapper fails a
test instead of quietly reopening the hole.

## The limit of what lint can guarantee

**The rule does not flag object properties.** This was established by probe, not assumed: a
file containing exactly `export const PROBE = [{ label: 'Hello World' }]`, inside the
enforced surface with `mode: 'all'` and `object-properties.include` naming `label`, produces
no finding.

So a lint rule cannot keep copy out of a data structure here. Two things cover that gap
instead:

- **Type, not convention.** `constants/navigation.ts` stores `labelKey` and `groupKey`, not
  `label` and `group`. Copy cannot sit there and be rendered, because the consumer resolves
  the field through `i18n.t`. A bare string becomes a key that does not resolve, and the
  test below fails on it.
- **The key-resolution test**, which reads every call site out of the source.

Where a screen still holds copy in a local const -- the home status chips -- it was migrated
by hand, and nothing but review will stop it coming back.
That is the honest boundary, and it is why this section exists rather than a claim that the
rule covers everything.

## What stays a literal, and why

Not every string in a screen is copy. Two kinds carry a targeted
`eslint-disable-next-line` naming what they are:

**Placeholder data.** Screens that are not yet wired to the Pond render stand-in values:
the Schedule screen's timeline and its fixed week (#14), the App Integrations list (#13).
Translating these would put fake data in the catalogue as though it were copy. They are marked as placeholders and go when the screen gets real data —
so the disables double as a to-do list of what each screen still owes.

**Product names and marks.** `Goose`, `Goose 2`, and the `G` letter used as the Goose mark
are not translated.

If you are adding a literal and it is neither of those, it is copy, and it needs a key.

## What the rule cannot catch

It reads literals, so it only sees what is written as one. Copy composed at runtime is
invisible to it: `app/(stack)/logs.tsx` builds its tab labels as
`tab.charAt(0).toUpperCase() + tab.slice(1)` over an enum, which is untranslatable by
construction and will never be flagged.

Nor can it see an identifier rendered as if it were copy. `{item.category}` on the old Memories badge
and `{room.name}` for the Devices fallback room both put an id on screen through a variable. The
fix is a label function over the id -- `segmentLabel`, `roomLabel` -- and ids that cannot be mistaken
for words: the fallback room is `room.unassigned`, not `Unassigned`, which also stops it merging
with a room a household really called that.

`models/` is also outside the rule. It holds fixture data rather than JSX, and that data is
scheduled for deletion as screens are wired to real endpoints.

## Adding copy

1. Add a key to `services/i18n/locales/en.json`, in the namespace for the screen or area.
2. Use `i18n.t('namespace.key')`, or `t()` where the file already uses `useTranslation`.
3. For interpolation, `i18n.t('devices.countMany', { count })` with `{{count}}` in the
   catalogue.

`services/__tests__/i18n.test.ts` reads every `t('…')` call site out of the source and
asserts each key resolves. This matters because i18next answers a missing key with the key
itself, so a deleted key does not throw — it ships, and a user sees `pairing.codeTitle`
where a sentence should be.

The test does not check the reverse direction. An unused key is dead weight but harmless,
and keys can be selected dynamically, so flagging them would produce false alarms.

## On translating into a second locale

There isn't one yet, and nothing here assumes one is coming. What this gives you is that the
copy is now in a single file rather than scattered across 24, so adding a locale becomes a
translation job rather than an archaeology job.
